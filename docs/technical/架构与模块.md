### 2.3 协议 handler 与缩略图信号量

```
mangashelf://localhost/object/{oid}/{cover|thumb|image}/{imgid}?v=…
  lib.rs:91   url = request.uri()
  lib.rs:98   std::thread::spawn          ← 每请求一线程，避免阻塞 WebView2 主线程（注释 94-96）
  lib.rs:100  resolve_image_url(svc, url) → (path, Option<(w,h)>)
    ├─ Some(size)：
    │    lib.rs:106  kind = "{w}_{h}"
    │    lib.rs:107  cached_thumb_path(...) 命中 → read_file_response（不占许可）
    │    └─ 未命中：sem.acquire()(112) → get_thumbnail_path(113) → 失败回退原图(115) → sem.release()(116)
    └─ None：lib.rs:120 read_file_response(path)   ← 原图直出
  lib.rs:131  responder.respond(response)
```

- 信号量为自实现计数信号量（`Condvar` + `Mutex<usize>`，lib.rs:24-52），全局单例用 `OnceLock`（lib.rs:54-58），许可数 `THUMB_CONCURRENCY = 2`（lib.rs:22）。
- 注释给出的理由：详情页首开时上百请求同时涌入，逐个裸跑 Lanczos 会吃满核心（lib.rs:18-21）。
- 缓存命中路径**不取许可**，即"重活限流、轻活直通"（lib.rs:104-118）。

### 2.4 图片响应与 MIME（lib.rs:212-247）

| 函数 | 行为 |
| --- | --- |
| `read_file_response(path)` | `std::fs::read` 整文件读入内存 → 200 + `Content-Type` + `Cache-Control: max-age=3600`；读失败 → 404 + `File not found` |

## 4. service.rs（1632 行）— 业务门面

### 4.1 结构与并发控制

| 项 | 内容 | 行号 |
| --- | --- | --- |
| 状态 | `db: Mutex<Database>` + `migrating: AtomicBool` | 21-26 |
| 锁习惯 | 一律 `.unwrap_or_else(\|p\| p.into_inner())`；理由：单语句/事务级原子操作，毒锁可安全恢复 | 5-6 |
| 迁移独占 | `begin_migration()` 用 `compare_exchange(false,true)`，返回 `MigrationGuard`；`Drop` 复位（panic 展开也复位） | 96-101、29-35 |
| 写入口守卫 | `ensure_not_migrating()`：`import_directory`(675)、`import_single_files`(854)、`delete_object`(564)、`apply_verify_fixes`(330) | 104-109 |

纯 DB 写（改名、标签、封面、进度、系列、书签）**不**受迁移独占保护——迁移第 ② 步已释放锁，
这些写会落在 `.bak` 之后（[handoff](../../handoff.md) §2.3 记录的副作用）。

### 4.2 查询与封面

- `get_object`（172-199）：三次查询（行、标签、图片）后组装；`first_image = images.first()`。
- `resolve_cover(obj)`（430-448）：显式 `cover_image` 且文件存在 → 用它；否则 `first_image` 且存在 → 用它；再否则回查 `get_images` 取首图。三级回退都要求 `is_file()`。
- `prune_thumbnail_cache`（210-224）：锁内取全部封面路径 + 图片路径作为 keep 集合，锁外调 `thumbnail::prune_thumb_cache(cache_dir, keep, 2GB)`。

### 4.3 库校验与修复

`verify_library`（230-325）**只读**：

1. `storage_root` 缺失/不可访问 → Err（231-234）。
2. 短锁快照：对象 + 其图片 `(filename, filepath)`（237-251）。
3. 锁外逐对象扫盘：目录是否存在、登记但缺失、磁盘有但未登记（259-301）；`images.is_empty()` 也算异常（290）。
4. 孤儿目录：库根下非隐藏、是目录、且不在已知 `normalize_path` 集合中（304-316）。

`apply_verify_fixes(plan)`（329-423）三类操作各自**复查后执行**，天然幂等：

| 阶段 | 动作 | 幂等依据 | 行号 |
| --- | --- | --- | --- |
| ① 移除失效行 | 重新过滤 `!is_file()` 才 `delete_image` | 以文件系统现状复查 | 336-353 |
| ② 补登记 | `collect_images` 与已登记文件名的差集，序号从 `next_sort_order` 起**本对象内连续**递增 | 以 DB 现状复查 | 356-391 |
| ③ 删除空对象 | 目录缺失或全部图片文件不存在才删；`delete_object(oid,false,root)` 不删文件 | 复查后删除 | 393-416 |

### 4.5 导入三段式（service.rs:661-812）

```
① 短锁（683-721）
   is_new：dir = <root>/<name>
     ├─ storage_path_taken → Err「存储目录已被其他对象占用」
     ├─ 目录已存在且非空（且不属于任何对象）→ Err（防误删）       692-700
     ├─ create_dir_all → create_object（false=ID 冲突：删刚建目录后 Err） 706-713
     └─ set_tags
   追加：resolve_append_target_dir（storage_path 有效则复用，否则按名重建并写回 DB） 622-651
② 无锁（723-770）
   collect_images → sort_start = next_sort_order
   .thumb 封面（仅 is_new）：find_thumb_cover → copy_image_keep_name（失败仅 warn）
   逐张 copy_image_keep_name，支持 cancel_check / progress_cb
③ 短锁（772-793）
   插入 images（uuid + sort_start+i）；is_new 且 cover_image 为空时：.thumb 优先，否则首图

```

`rollback_import`（817-844）逆序清理：新建对象则删对象（级联删图行），追加则逐条删本次新增图行 → 删本次建的目录 → 逐个删已复制文件。

`import_single_files`（848-915）同构：过滤点开头的隐藏文件 → 按 `natural_key` 排序 → 复制（失败不占序号，`sort_start + ok`）→ 入库；失败走同一回滚（`created_object=false`）。

### 4.6 系列与书签

- `set_series_for_object`（480-501）：`series_name` 为空/None → `series_id=NULL`；否则按名 `get_or_create`；同系列卷号冲突直接 Err「该系列已存在卷 N：「对象名」」；写后 `prune_empty_series`。

### 5.2 协议 URL 解析（commands.rs:638-692）

1. `url.split(['?','#']).next()` 去掉查询串/片段——否则 `cover?v=xxx` 会被当成 kind（640-641；测试 829-857 固定该行为）。
2. 定位 `"/object/"`，取其后的路径（643-646）；`split('/')` 得 `["object", oid, kind, img_id?]`（649-655）。
3. `cover`：`get_object` → `resolve_cover` → 文件名小写以 `.thumb` 开头则直出原图（无尺寸），否则按 `COVER_THUMB_SIZE(180,240)` 生成（657-675）。
4. `thumb`：`get_image_by_id(oid,img_id)` → `GRID_THUMB_SIZE(160,160)`（676-689）。
5. `image`：同查 → 无尺寸 → 原图直出（687）。
6. 其他 kind → Err「未知的图片类型」；缺 img_id → Err「缺少图片 ID」（677-680、690）。

`parse_thumb_kind`（695-703）把 `"{w}_{h}"` 解析成尺寸，失败回退 `THUMBNAIL_SIZE(220,300)`；
实际 kind 恒由同一 `size` 拼出（lib.rs:106），回退分支仅在手工构造 URL 时可达。

## 7. thumbnail.rs（421 行）

### 7.1 缓存键（thumbnail.rs:22-49）

```
prefix = hex(sha256("v2:" + source_path + {(w, h) 的 Debug 形式})[..16])   # 32 字符，含生成器版本
file   = "{prefix}__{mtime_nanos}_{len}.jpg"                                # 取不到 metadata 时退化 "{prefix}.jpg"
```

- `THUMB_GEN_VERSION = 2`：v2 加入 EXIF 方向校正，版本参与哈希让旧缓存整体失效（22；测试 283-319）。
- mtime+size 参与文件名：源图被替换后旧缓存不再命中（33-49）。

### 7.2 生成流程（thumbnail.rs:68-145）

| 步骤 | 内容 | 行号 |
| --- | --- | --- |
| 前置 | 文件不存在 / 扩展名不受支持（`is_supported_image("x"+ext)`）→ None | 73-84 |
| 命中 | 目标文件已存在直接返回 | 86-89 |
| 解码 | `ImageReader::open → into_decoder`；`decoder.orientation()` 读 EXIF；`from_decoder` 后 `apply_orientation`；转 RGB8 | 93-100 |
| 缩放比 | `scale = max(target_w/src_w, target_h/src_h)`（覆盖目标的最小放大比） | 106-108 |
| **双滤波** | 大比率（任一维 `src >= new*2`）用 `thumbnail()`（box 单趟，快数倍）；结果比目标小则 `resize_exact(..., Lanczos3)` 补齐；小比率直接 `resize_exact(..., Lanczos3)` | 114-128 |
| 裁剪 | `crop_imm` 居中裁剪到目标尺寸 | 131-133 |
| 落盘 | JPEG 编码到内存 → 写 `*.tmp` → `fs::rename` 原子替换 | 136-142 |

注释解释双滤波动机：Lanczos3 核宽随缩小比放大（约 13× 时每输出像素 80+ 采样点），是最大 CPU 热点（110-113）。

### 7.3 清理

## 8. library_manager.rs（557 行）

### 8.1 路径工具

| 函数 | 行为 | 行号 |
| --- | --- | --- |
| `check_writable(path)` | 目录不存在 → Err；写 `.manga_shelf_write_test` 再删（会留下瞬时文件；`get_state`/`setup` 每次调用都执行） | 32-40 |
| `normalize_path(path)` | `fs::canonicalize`（失败则原样），Windows 下 `to_lowercase`；路径比较的唯一入口 | 46-54 |
| `is_relative_to(path,parent)` | 先 normalize 再 `strip_prefix`，要求剩余部分非空 → `D:\Manga2` 不会被判成在 `D:\Manga` 内 | 56-64 |
| `map_path(path,old,new)` | normalize 后 `starts_with`（**字符串前缀**）→ `strip_prefix` → join 新根；不在旧根下则原样返回 | 66-77 |

> ⚠ `map_path` 仍用字符串 `starts_with`，与 `is_relative_to` 的组件级判定不一致：旧根 `D:\Manga`、
> 图片路径 `D:\Manga2\…` 时会被错误重写。迁移前 `prepare` 已用 `is_relative_to` 拒绝根目录互相包含，
> 但对象目录之外的"库外路径"（warnings 分支）可能命中该前缀问题。

### 8.2 三阶段迁移

`prepare_library_migration`（79-157）——纯计划，不写盘：

1. `canonicalize` 新旧根；相同 → Err「新旧图库目录相同」；互相包含 → Err「新旧图库目录不能互相包含」（92-97）。
2. `check_writable(new_root)`（99）。
3. 逐对象：`storage_path` 非空且目录存在（否则 Err，点名对象）；目标目录重名自动 `"{name} ({n})"`（114-130）；`map_path` 重算全部图片路径与封面（132-143）。

`migrate_library`（194-324）：

| 阶段 | 锁 | 动作 | 行号 |
| --- | --- | --- | --- |
| ⓪ | — | `begin_migration()` 取独占位（RAII） | 202 |
| ① | 持锁 | `prepare` 出计划；`checkpoint(TRUNCATE)` → 复制主库到 `.bak.tmp` → 改名 `.bak`；失败即中止（尚未移动任何目录） | 208-225 |
| ② | **无锁** | `create_dir_all(new_root)` → 逐个 `fs::rename(old_dir,new_dir)`，成功即记入 `moved_dirs` | 254-275 |
| ③ | 短锁 | 手动 `BEGIN` → 更新 `storage_path`/每张图 `filepath`/封面 → `set_config(storage_root)` → `COMMIT`；失败 `ROLLBACK` | 280-307 |
| ④ | 无锁 | 删旧根 `.thumbcache`；删 `.bak`（**仅成功路径**） | 314-321 |

失败统一走 `migration_failed`（182-192）：先 `rollback_moved_dirs`（164-178，**逆序**送回；原位被占 / 新位已消失 / rename 失败三种异常都计入清单而非静默跳过），有回滚失败才附「请手动恢复」清单。COMMIT 失败也走该出口（301-310）。

库外路径（`map_path` 返回原值）不阻断迁移，只收集为 `warnings` 并去重（232-245）；返回值 `(plans.len(), warnings)`（323）。
